## Architecture

One play format. Three producers (builder, PDF importer, seed data), one animator, three
consumers (builder preview, review flow, quiz engine). The importer's job is to produce
exactly what the builder produces; the quiz engine never knows where a play came from.

Singletons that must never be duplicated — if positions or validity are computed in two
places, one of them is wrong:

- `src/lib/timing/positionsAt.ts` — `positionsAt(play, beatIndex, t, phase)`. Pure. No refs,
  no mutation, no component state. Every consumer calls it.
- `src/lib/play/validation.ts` — `validatePlay()`. Runs in the builder on every edit, in the
  importer before save, and before a play is quizzed.
- `src/components/court/CourtRenderer.tsx` — the only renderer.
- `src/components/animator/PlayAnimator.tsx` — the only animator.

### Coordinates

500 × 470, baseline at **top** (y=0), half court at bottom. Hoop (250, 52.5), lane x=170–330.
Constants live in `src/lib/play/geometry.ts`; the SVG line geometry in `src/lib/court/`.
The same system is mirrored in `services/importer/derive.py` and in the AI skill file, so a
change to the court must be made in all three.

### Beat semantics — the easy thing to get wrong

`Beat` carries two position maps and two ball fields:

- `startPos` / `startBall` — parser observations at the **start** of the frame.
- `pos` / `ball` — state at the **end** of the beat, i.e. the next frame's start.

`normalizeSeedPlay()` (`src/lib/play/normalize.ts`) resolves a beat's `pos` from the *next*
beat's `startPos`, which is what makes drawn arrows line up with FastDraw frames. Animation
interpolates `startPos → pos`; `ball` is derived, never hand-authored.

### Timing

The coach never sets timing. `sequenceBeat()` (`src/lib/timing/sequence.ts`) assigns each
action a default lane by classified kind (screen / cut / cut-off-screen / dribble / roll /
handoff / pass), pushes start times later per the dependency rules, then rescales so the last
action ends at 1.0. Playback is two phases per beat: MOVE (t 0→1) then a mandatory HOLD.
The ball is its own entity computed every frame — never "attached to player X" at render time.

### Import pipeline (`services/importer/`)

1. `parser.py` — deterministic, free, verified 36/36 on a real FastDraw export. **Do not
   rewrite it.** Extracts court bounds, five positions per frame, possession from the circled
   number, play names, frame order.
2. `interpret.py` — one Claude vision call per frame crop. Loads
   `docs/skills/play-interpretation.md` **at runtime** so the prompt can be tuned without a
   deploy. The model reads arrows only; it never estimates positions.
3. `derive.py` — the single writer of `beat.ball` and of movement actions the AI missed.
   Anything it invents is marked `derived: true`; validation rule 11 caps the derived ratio.

`scripts/rebuild-seed-plays.py` and `scripts/run-interpret-v2.py` re-run this pipeline into
`src/data/`. `plays-interpreted.json` is the canonical seed everything imports; the `-v2` /
`-v3` files are re-interpretation experiments kept for comparison, not consumed by the app.

## Conventions

- Path alias `@/*` → `src/*`. Tests live outside tsconfig's `include`, so they import with
  relative paths and explicit `.js` extensions (`../../src/lib/play/normalize.js`).
- Tests use the built-in `node:test` runner via `tsx`. No Jest/Vitest.
- The play engine (`lib/play`, `lib/timing`, `lib/court`, `components/`) is TypeScript. Auth,
  landing page, and Supabase glue are still `.jsx`/`.js` — that split is deliberate, not debt
  to clean up opportunistically.
- `_legacy/` is the previous build, excluded from tsconfig and eslint. Read it for reference;
  don't import from it. `tools/poppler/` is a gitignored local binary drop.
- Dev harnesses: `/dev/animator` (play picker, speed, step mode, per-beat action table),
  `/dev/court` (static render check), `/dev/repairs` (crop vs. our render, for import review),
  `/plays/new` (builder).

## Rules for the whole build

- Never save, animate, assign, or quiz on a play where `valid` is false.
- No AI calls during a quiz session, ever.
- All progress data in Postgres (Supabase). localStorage only for the logged-out demo.
- AI context files live in `docs/skills/` and are loaded at runtime, never pasted into code.
- The product teaches memorization only — where to line up, where to go, who gets the ball.
  Reads, decisions, and basketball IQ are permanently out of scope. Every question must have
  one objectively correct answer checkable against the play data.
